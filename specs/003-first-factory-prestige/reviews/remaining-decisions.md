# Remaining Feature 003 gameplay decisions

**Date:** 2026-09-29  
**Status:** Approved by the owner on 2026-09-29 — all recommendations accepted except machine removal, which uses a partial refund (see spec.md Clarifications).

| Topic | Recommended rule and reason | Viable alternative / cost |
|---|---|---|
| Machine removal and replacement | Removal requires confirmation, gives no Cash refund, drops that machine's cycle progress, and frees its slot. Replacement is remove then build, each atomic. This prevents build/resale loops that inflate Factory Value. | Refund a documented fraction of construction cost; also subtract that value from invested assets and prove no prestige-value exploit. |
| Mid-cycle level and speed change | Preserve completed fraction of the current cycle and recalculate remaining time under the new duration at the action/effect boundary. No input/output moves until atomic completion. | Keep the old cycle duration until its next completion; simpler, but immediate upgrade feedback is delayed. |
| Completion and selling order | At each simulation timestamp: expire real-time effects/deadlines, resolve due completions in player priority order with atomic net-capacity checks, perform enabled auto-sales of resulting stock, then start/progress subsequent cycles. Player-issued delivery/purchase/build commands apply at their timestamp after the preceding simulation interval. This makes auto-sell a real choice: sold intermediate stock is unavailable next cycle. | Sell each output immediately during completion; would make producer order affect same-timestamp downstream availability more strongly. |
| Contract loop | Offer three deterministic contract types (Plate, Gear, timed Bar) once unlocked; at most one active. Player accepts and explicitly delivers from available stock. Deadline is inclusive (delivery at deadline succeeds); expiry after deadline grants no reward/penalty. Completed or expired offers can be accepted anew with content-defined scaling, but no random offer generation. Cash/RP/Item reward is one atomic grant. | Randomized offers require seed/persistence; simultaneous active contracts complicate reservation and presentation. |
| Item acquisition and stacking | Contracts grant Items through deterministic milestone/reward definitions; all three tiers become obtainable during the first run. One active instance of an identical effect per target; a conflicting activation is rejected without consumption. Different effect categories and Overdrive compose multiplicatively with content-defined bounds, and durations use real UTC. | Refreshing/stacking identical effects needs additional policy and can trivialize progression. |
| Overdrive availability | Start ×2 speed for 30 s and a content-defined five-minute real-time cooldown; cannot reactivate while active. Cooldown and effect continue offline, reset on prestige. | No cooldown allows continuous active boosting; a shorter cooldown changes the 2-hour balance substantially. |
| Factory Value | Count current Cash + all stored stock at current market value + historical Cash actually paid for *currently owned* machines and their upgrades + current factory/storage expansion upgrades. Removed machines do not contribute. Research/contract rewards and spent Items have no separate valuation. Use exact whole-Cash arithmetic and floor only at the final IP calculation. | Count only slot/storage expansion investments; makes the $10M threshold harder and devalues machine upgrades. |
| Numeric scope | Store resource units, Cash, RP and IP as exact nonnegative integers up to a documented checked 64-bit bound for Feature 003; reject overflow atomically. Format high values with full exact value on inspection plus a short scientific/suffix display. Future 1e150 requires an explicit numeric/save/content migration. | Implement arbitrary-size integer/fixed-decimal representation now; increases serialization and performance work for a first-run $10M target. |
| Starting balance and proof | Author a versioned initial content sheet with start Cash, build/factory costs, unlocks, contract cadence/rewards, all Item grants, Research graph and Industry cost/cap. Treat its numbers as a hypothesis. A deterministic scripted active policy must log 10/15/30/60/90/120-minute states; an independent human playtest validates the feeling. Revise content and obtain owner approval before claiming the 2-hour and second-run targets. | Approve every number now without simulation; high risk because the draft's base chain yields at most $21,600 in two hours when selling Gears. |

2. Sum dev.input and dev.output across buffers into global Ore and Bar. Map each dev.machine.basic to a Smelter in a stable fixed slot, keep active state and instance identity, and map progress as floor(oldProgressTicks × 2 / 5). No other IDs have a mapping.
3. Reject an unsupported ID, overlapping/unrepresentable machine, more than the initial four slots, mapped stock above 1,000, arithmetic failure or invalid clock without truncation, refund or partial publication. Explain how to recover the old V1 generation.
4. Write/validate/promote a complete V2 candidate once, then publish it. The prior V1 generation remains recoverable. Retry must detect an already-promoted migration and avoid a second offline credit.

This import changes the production recipe and machine duration by explicit owner choice. It preserves mapped quantities and proportional progress, not the old development scenario's exact future production behavior.
