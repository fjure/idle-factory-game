**Release-note text for T133 (OD-7), recorded here for T133 to copy:**

> **Save compatibility between Feature 002 and Feature 003 builds (development saves only).**
> Feature 003 keeps its progress in its own save folder, `IdleFactory/Checkpoints/v2/`. On the first start it imports the Feature 002 save from `IdleFactory/Checkpoints/v1/` once. It never changes the `v1/` files. The two builds do not share progress after that import:
> 1. **Feature 002 build after the import.** A Feature 002 build reads only `v1/`. It shows the factory as it was at the import and does not see any Feature 003 progress. That progress is not deleted; it stays in `v2/`.
> 2. **Feature 003 build after a Feature 002 build saved to `v1/`.** Feature 003 never imports again once a valid `v2/` save exists. Progress that a Feature 002 build saved to `v1/` after the import is ignored and is lost to Feature 003.
>
> Use one build per device and test profile. To start Feature 003 again from newer Feature 002 progress, copy the `IdleFactory/Checkpoints/v2/` folder somewhere safe, then delete it; the next Feature 003 start imports the current `v1/` save again. This discards the Feature 003 progress. Neither build detects or warns about a mismatch.

### 6. T250: desktop focus loss writes one safety checkpoint

Mechanism (code): on a desktop class, `RunLifecycleAdapter.NotifyDesktopFocusChanged` calls `WriteSafetyCheckpoint` on each true-to-false edge of `desktopFocused` (a repeated false is ignored). `WriteSafetyCheckpoint` returns when not configured, when quitting or when a departure was recorded; it calls `prepareForSafetyCheckpoint` (`FactoryRuntimeHost.FlushActiveInterval`, which advances the run to now without stopping), increments `SafetyCheckpointAttempts`, then calls `RunPersistence.Autosave()`. `Autosave` is a successful no-op while a prestige is pending or the lifecycle is not `Running`; otherwise it is `SaveNow` and `SaveCheckpoint`: new checkpoint ID, generation + 1, `departure = max(clock, timeline, active departure)`, then `SafePromote` through the unchanged protocol. The lifecycle stays `Running` and `departureRecorded` stays false; `ResumeAndReconcile` is never called, so there is no reconcile and no summary.

Tests: `WhilePrestigeIsPending_SaveNowIsRejected_AutosaveSkips_AndNoCheckpointIsWritten`, `Autosave_WritesAGeneration_WhenNothingIsPending`, `WhilePending_SaveNowIsRejected_AutosaveSkips_AndASuspensionAndReturnNeitherCreditNorAwardTwice`, `BeforeResume_TheRunIsLifecycleBlocked_AndOnlyResumeIsAdmitted`, `DesktopRegularShutdownRecordsTheDepartureAndTheNextStartCreditsTheIntervalOnce` (focus loss, then quit), `SaveNow_DepartureIsTheLaterOfTheClockAndTheRunTimeline` | The reverse order (quit, then focus-lost) is guarded in code but no test drives it. The skip conditions are proven at `RunPersistence` level, not through the adapter. Both are low risk. | Accept |
| T250-5 | Failure handling | Disk full, permission loss or an antivirus lock makes the safety write fail; the host flush throws | A silently stale save; an exception inside a Unity callback | A failed write is a typed rejection (`EveryStorageFailure_IsATypedRejection_NotAnException`, `SaveNow_WithFailingStorage_IsATypedRejection_AndTheOldGenerationStaysAuthoritative`); `RunPersistence` sets the persistence status to Failure with static copy, the old generation stays authoritative, and `LastSafetyCheckpoint` keeps the failed result. The contract states a failed write changes only the persistence status. The adapter does not retry; the next focus loss or the quit tries again. | **F-2.** No test drives a failing write through `RunLifecycleAdapter.WriteSafetyCheckpoint`; the T250 tests all assert `IsSuccess`. If `prepareForSafetyCheckpoint` threw, the exception would escape `OnApplicationFocus`; Unity would log it, and neither the count nor the write would run. Neither path loses data beyond the staleness already accepted. | Accept with advisory |
| T250-6 | Crash window and long unfocused sessions | The player leaves the window for hours (Run In Background is on) and the process dies | Loss of everything after the last focus-loss checkpoint beyond the eight-hour cap | The cap bounds the recovered credit to 8 h at offline efficiency. Compared with the pre-T250 departure semantics, a focus-loss followed by a crash recovers the same amount. | **F-3.** Before T250 the simulation stopped on focus loss; now it keeps running unfocused for an unbounded time with no periodic save (Feature 001 A-005 has no timer autosave). A crash after, say, 20 unfocused hours rolls back to hour 0 plus 8 h at reduced efficiency. This is an owner-visible consequence of the T250 decision, not a security defect. Mitigation if wanted: a coarse timer autosave (for example every few minutes while unfocused) through the same `Autosave` command. | Accept with advisory |
| T250-7 | Clock use by the safety write | Clock set forward before the focus loss | The stored departure is ratcheted into the future | `departure = max(clock, timeline, active.Departure)` never moves backward, so a later honest clock yields `BackwardClock` and zero credit, never extra credit (S1-6). | Self-harm only. | Accept |
| T250-8 | Platform seam | A phone or tablet takes the desktop path, or a desktop takes the mobile path | A mobile player loses the departure checkpoint on focus loss, or a desktop reconciles on Alt-Tab | `LifecyclePlatform.IsMobile` is `Application.isMobilePlatform` (not the input profile); `Override` is for tests and restores on dispose. `runInBackground: 1` is the deliberate setting change (`ProjectSettings.asset`, line 90). Tests: `ThePlatformSeamFollowsTheOverrideAndRestoresThePreviousValue`, `TheMobileClassStillRecordsADepartureOnFocusLossAndReconcilesTheReturn`, `TheDesktopLifecycleTestsRunInTheEditor` | The mobile code path is unchanged; the on-device effect of the global `runInBackground` setting is covered by the Android journey evidence, not by this review. | Accept |

**Scenario 6 verdict: Accept with advisories (F-1, F-2, F-3).** The write is as safe as any other save; the open points are throttling, one test gap and the absence of a timer autosave.
