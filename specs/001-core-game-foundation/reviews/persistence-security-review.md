## Finding

### P2 — Interrupted promotion can invalidate the retained previous generation

**Threat/failure scenario:** after two or more successful saves, the next promotion writes the candidate into the data slot opposite the active slot. That is also the slot named by the existing manifest's `Previous` reference. If the write or flush is interrupted before the new manifest is durably published, the old manifest remains selected but its previous reference now points at overwritten or partial bytes. The active checkpoint remains readable, but the explicit previous-generation recovery option is lost.

`JsonCheckpointStore.Publish` selects that opposite data slot at [lines 254–261](../../../Assets/IdleFactory/Unity/Persistence/JsonCheckpointStore.cs#L254), writes it before publishing the new manifest at [lines 263–269](../../../Assets/IdleFactory/Unity/Persistence/JsonCheckpointStore.cs#L263), and only constructs/publishes the new selector afterward. The persistence contract says a failed pending write leaves the existing active **and previous** generations unchanged and requires explicit recovery to preserve the previous source ([contract lines 87–94 and 119–127](../contracts/persistence-v1.md#L87)). The store regression test currently codifies the contrary behavior: after a torn third promotion, the latest active survives but `ReadPrevious()` fails ([CheckpointStoreTests lines 231–245](../../../Assets/IdleFactory/Tests/EditMode/CheckpointStoreTests.cs#L231)).

**Impact:** an ordinary storage fault or process/device interruption during a later save can remove the last older recovery point. The immediately active save is preserved and is not silently rolled back, so this is bounded recovery-data loss rather than corruption of the authoritative live generation. The contract and implementation/test expectation need reconciliation; this review does not change save semantics or implementation.
