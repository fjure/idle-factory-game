A. Autoconnect build (CoreGameFoundation-t064-gles3.apk, Development | ConnectWithProfiler, as T040)

2. trial 09:22-09:27  After a reconnect and pressing the window's record button, 438 frames arrived in 20 s.
   ProfilerDriver.enabled alone never records: the Unity 6000.6 profiler window owns the recording state
   (ProfilerWindow.SetRecordingEnabled). A player memory snapshot and per-asset residency worked.
3. discarded-run-1-attach-during-scene-load 09:28  Attached at about +2 s; 0 frames in 60 s; the snapshot request
   never completed and blocked all later snapshots ("another snapshot in progress") until the profiler restarted.
3b. trial 09:34  Fresh launch, attached after "Fully drawn" (+13 s) and recording at once: frames arrived (882 in
   about 60 s). A snapshot request then failed at once because attempt 3's request still blocked the profiler.
4. discarded-run-1b-idle-connection 09:38  Attached after "Fully drawn" (+14.3 s); 0 frames in 60 s.
5. discarded-run-1c-autoconnect-recording-at-attach 09:41  Recording on at attach; 0 frames.

Root cause (observed 09:41-09:44): the autoconnect player opens its own profiler connection to the build host at
startup ("Starting connection attempt to host ... Successfully connected to host after 6 seconds"). netstat showed
qemu-system-x86_64 (the emulator guest) connected to 192.168.2.172:34999, owned by the MAIN editor. Removing the
editor's `adb reverse tcp:34999 tcp:34999` did not change it: the player then connected through the emulator NAT
directly. Both the main editor and the standalone profiler listen on 0.0.0.0:34999, so which process receives the
player's own connection is not controllable; the player streams to that connection and the standalone profiler's
Direct IP connection received nothing. The main editor must stay open, because the standalone profiler is its child
process. This is also the most likely mechanism of the T040 stall: the autoconnect player was already connected to
the editor when the editor opened a second Direct IP connection.
